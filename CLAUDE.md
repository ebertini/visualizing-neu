## What this project is

An exploratory **data-visualization project on Northeastern University's faculty funding and grant history** (window ~1995–2026, ~$2.18B in awards). The deliverable is an interactive visualization telling the story of NEU grant funding. Current work is EDA + topic modeling in Jupyter notebooks published to GitHub Pages. A dual-mode **Plotly Dash** dashboard (touchscreen **kiosk** build + responsive public browser build from one codebase) is still a possible final goal, but that direction is under-defined and `docs/WEEKLY_PLAN.md`, which used to describe it, is now deprecated.

**Two parallel visualization tracks publish into `docs/onlineoutput/` — know which is whose before editing either.** `docs/EnricoVis/` (`grant_atlas`, `topic_islands`, `topic_hierarchy`) is a **parallel effort by the PI** — read-only reference / inspiration, not something to casually modify. `docs/TopicVizPrototypes/` (`topic_flow`, `what_we_can_see`) is **the user's own** topic-model visualization work, built to reinforce their own analysis — it reuses EnricoVis's canonical BERTopic output as a read-only upstream input (see `src/build_viz_aggregates.py`) but writes only into its own directory. Both are "best current sense of what the final deliverable could look like" — EnricoVis for the spatial-embedding forms, TopicVizPrototypes for time/coverage forms EnricoVis doesn't cover.

## The data pipeline (`src/build_dataset.py`)

Reads 6 raw files from `DataSet/`, cleans/joins, and writes 7 tables to `data/processed/` (each as `.parquet` snappy **and** `.csv` utf-8-sig for Excel), plus `PIPELINE_VALIDATION.txt` (authoritative row counts + coverage). Run it whenever raw data or logic changes; notebooks auto-pick up the new parquets.

**Canonical output tables** (see `src/README.md` for full column dictionary):
| Table | Rows | Grain |
|---|---|---|
| `faculty.parquet` | 2,247 | one per faculty (2,232 HR roster + 15 `UnmatchedFaculty.csv` supplement) |
| `grants.parquet` | 2,676 | one per `grant_id`; abstract text merged in |
| `faculty_grants.parquet` | 3,144 | one per (faculty, grant) link; the join table |
| `grant_orphaned_abstracts.parquet` | 5,095 | abstracts not matched to any NEU grant |
| `faculty_missing_metadata.parquet` | 13 | grant-active faculty absent from HR (backfill worklist) |
| `faculty_id_lookup.parquet` | 2,247 | faculty_id → college/dept/AAUID |
| `personid_to_faculty.parquet` | 1,042 | the ID bridge (see below) |

**Key logic:**
- Column headers normalized via `_lower_cols`; academic ranks collapsed to ~8 buckets via `_normalize_rank`.
- Faculty **names come from grant tables** (mode/most-common `personname` per id), **not** from HR.
- AAD federal-coverage merged onto grants by **fuzzy agency-name match** (`rapidfuzz token_set_ratio`, **threshold 85**).
- Abstracts matched to grants on `sourceactivityid == grant_id`, keeping the **most-recently-updated** record per grant; non-matches become orphans.
- `personid_to_faculty` uses a **strict 100% co-occurrence majority vote** (a personid resolves only if exactly one faculty shares 100% of its grants); ties/zero → unresolved.

## Identifiers — read this, it's the #1 source of bugs

- **Canonical keys: `faculty_id` and `grant_id`.**
  - `faculty_id` = HR `Employee ID` = `ClientFacultyId` in grant tables.
  - `grant_id` = `grantid` in grant tables = `sourceactivityid` in the abstract table.
- **`"00000"`** is the reserved sentinel for grant rows whose `ClientFacultyId` was missing (currently resolves to 0 rows after cleaning, but the code path exists).
- **The `PersonId` trap:** two raw files have a `PersonId` column that are *different ID spaces with zero overlap* — `grants-with-coPI.PersonId` is the **AAUID** (Academic Analytics vendor id), `grants-with-abstract.PersonId` is an **internal upload-system id**. Neither joins directly to `faculty_id`. To go from an abstract `personid` to a faculty, use `personid_to_faculty.parquet` only.
- **AAUID** is preserved on `faculty_id_lookup` for future enrichment but is **never a join key**.

## Analytical caveats — must be disclosed in any deliverable

1. **`$2.18B headline ≠ money NEU raised.** Grants get attributed to a faculty member even if the award predates their NEU hire (source marks everyone "Northeastern"). Use **`faculty_grants.neu_status == 'earned_at_neu'`** for external/NEU-work reporting:
   - `earned_at_neu` (start ≥ hire): 2,098 rows / ~$1,408M
   - `prior_institution` (start < hire): 866 rows / ~$685M — does NOT count as NEU work
   - `unknown` (missing dates): 180 rows / ~$153M
2. **Funding-credit model matters.** PI-only vs full-credit vs fractional split materially reorder faculty leaderboards — always state which model a chart uses. (`src/README.md` has the three canonical snippets.)
3. **Data is NSF/NIH-skewed** (~88% of dollars). Internal/foundation/industry funding is largely invisible.
4. **Abstract coverage:** **2,390 of 2,676 grants (89%)** have usable abstract text as of the 2026-08-20 NIH RePORTER + NSF Award Search backfill (`src/backfill_nih_reporter.py`, `src/backfill_nsf_awards.py`, adopted gap-fill-only via `build_dataset.py`'s `_apply_abstract_backfill`) — up from 1,928 (72%) beforehand; only ~37% of the 8,075 abstract rows match a grant_id (unaffected by the backfill, a separate internal-upload-system stat). The **NIH abstract "cliff"** (near-0% coverage from 2020+), previously a **data-collection artifact, not a funding decline** that this caveat used to say only an NIH RePORTER backfill could fix — **is now closed**: 2020–2025 NIH/NIH-SubAward coverage runs 94–100%, live-verified. 5 grants (`abstract_source == 'nih_reporter_parent'`, a subaward's borrowed parent-center text) are excluded from the topic-model fit despite having stored, displayed text — see `src.clean_text.LOW_TRUST_ABSTRACT_SOURCES`. Missing the abstract still barely determines BERTopic assignment confidence, though the exact numbers moved and the comparison is now murkier: unassigned rate is **25.3%** for grants with an abstract vs **14.8%** for title-only grants (previously 28.0%/27.6%) — but this reversal is mostly a **composition effect**, not new evidence that titles got more informative: the remaining 286 title-only grants are now ~83% ONR/ARO/NASA/AFRO/DOE/NOAA, a far more homogeneous, easily-clustered population than the old, broader 740-grant title-only mix. See `notebooks/08_abstract_recovery_and_refit.ipynb`.
5. **"Unassigned" (no confident topic) — as of the 2026-08-29 keyword-classifier redo, this dropped from the single largest topic bucket by dollars to a small one.** Under the retired BERTopic fit it was **697 grants / $583M / 26.7%** of dollars (646 HDBSCAN noise + 51 in the flagged topic-14 artifact). Under the now-canonical curated keyword classifier it's **66 grants / $40.4M / 1.9%** of dollars (38 `no_keyword_evidence` — real text, zero curated terms fired, a genuine curation-coverage gap — + 28 `placeholder_title_only`, the same ONR "Grant"-titled records as before). Any topic-based chart must still show it, not drop it — it's just no longer the dominant bucket. See "Topic modeling — state of play" below.
6. Prefer `startdate`/`startdateyear` over `awarddate` (98% null). Use `totaldollars` from `ri_matches`, not the abstract file's unreliable `Dollar Amount`.
7. **External collaborators are invisible.** Every grant record is stamped "Northeastern" regardless of who else worked on it — there's no way to see co-investigators at other institutions, so any collaboration-network analysis from this data is NEU-internal only.

## Topic modeling — state of play

- **The curated keyword classifier (BM25F) is now canonical, replacing BERTopic, as of 2026-08-29.** The full topic-model redo (Plans A/B → Phase 4a curation → Phase 4b classifier → Phase 3 validation → downstream integration) went from "designed, nothing built" to fully implemented and wired into the live pipeline in one session. **31 leaves / 7 parents** (`outputs/topic_keywords.json`, `kw_curation.py --check` passing 0 errors), scored by `src/classify_by_keywords.py` (stdlib/pandas only — no torch/bertopic/umap/hdbscan, so it finally runs fully offline and reproducibly). Output: `data/processed/topic_keyword_assignments.parquet`. `outputs/topic_labels.json` is no longer BERTopic's own seed file — it's now that classifier's `--write-topic-labels` conversion of the curated taxonomy, so `src/build_viz_data.py` (unchanged read contract) now joins the keyword classifier's `kw_leaf_id` as the canonical `dom`/`isNoise` for every downstream consumer (EnricoVis JSON → `build_viz_aggregates.py` → `docs/TopicVizPrototypes/`). **BERTopic's own assignment is kept, not deleted** — `topic_assignments.parquet` stays byte-untouched, joined in as `bertopicDom`/`bertopicNoise` comparison columns on every point, exactly per the redo plan's "kept as a comparison column" decision.
- **Unassigned collapsed from 697 grants / 26.7% of dollars ($582.7M) to 66 grants / 2.5% of grants / 1.9% of dollars ($40.4M)** — by a wide margin the headline result of this redesign. Broken down honestly via a new `unassignedReason` per grant (`coverage.json`'s `unassigned.by_reason`, replacing the old HDBSCAN-noise/artifact-topic split, which no longer means anything under a keyword classifier): **38 `no_keyword_evidence`** (real text, but literally zero curated terms fired — a genuine curation-coverage gap worth a future curation pass, since only 856 of the ~2,506 pruned candidate terms survived Phase 4a curation) and **28 `placeholder_title_only`** (the same ONR "Grant"-titled records BERTopic's old artifact topic 14 held — unclassifiable by any text method, keyword or embedding). `ARTIFACT_TOPIC_ID` is **retired (`None`)** in `src/build_viz_aggregates.py` — every leaf in the curated taxonomy is a deliberate human decision, not an HDBSCAN byproduct, so there's no single hardcoded "flagged bucket" anymore.
- **A real matching bug was found and fixed post-hoc via manual spot review, not by any automated check** — worth internalizing as a lesson, not just a changelog line. `src/keyword_match.py`'s "collapsed" tier stripped ANY intra-token `-./+`, including a TRAILING symbol with nothing to bridge (the curated LIGO-era term `"a+"` collapsed to bare `"a"`), which matched the English article "a" throughout unrelated abstracts — confirmed concretely misrouting an antimicrobial-chemistry grant to "Gravitational Wave Detection & LIGO Instrumentation" at "medium" confidence. Fixed by only collapsing a separator with alphanumeric content on BOTH sides (`(?<=[A-Za-z0-9])[-./+](?=[A-Za-z0-9])`), same as the real bridging cases (`covid-19`→`covid19`, `pm2.5`→`pm25`) but not degenerate trailing/leading symbols. Re-running after the fix **improved every measured number**: parent-level BERTopic agreement rose 67.9%→**75.5%** (into the plan's "healthy" 0.70–0.90 band), low-confidence share dropped 26.6%→**19.9%**, unassigned rose slightly (100→114 grants) as the honest cost of no longer counting a false-positive match as evidence. A follow-up manual review of the 4 unassigned grants that DID have real abstract text found one genuine curation gap (grant 726280, "Visualizing Oral Histories of Bengal using Digital Humanities Tools") — adding `"oral history"` (df_corpus=1) and `"digital humanities"` (df_corpus=3) to Leaf 12 (Social Science & Public Policy) fixed it, and as a bonus corrected a real misclassification (grant 1619895 had been landing in the Predator-Prey ecology leaf via "ecology" used metaphorically, not literally) — down to 73 unassigned / 45 `no_keyword_evidence` after three total manual curation passes on the remaining title-only grants — materials/alloy, cancer-nanoparticle, bone/skeletal, military-funded ML, NOAA fisheries, humanities, traineeship, and network-science clusters (all added as new keywords to their existing best-fit leaf), plus a final pass that RELABELED three leaves as their scope broadened by human decision: Leaf 20 "Gravitational Wave Detection & LIGO Instrumentation" → "...& Observational Astrophysics" (absorbed a 10-grant NASA XMM-Newton/tidal-disruption-event research program), Leaf 23 "5G/mmWave & Cellular Wireless Communications" → "Wireless Communications, Antennas & Electromagnetic Metamaterials" (absorbed 4 ONR/AFRL antenna/metamaterial grants), and Leaf 18 "Algebra, Geometry & Mathematical Physics" → "...& Metascience" (absorbed 2 AFRL scientometrics grants) — one candidate grant (1777815, ambiguous chemistry/quantum-theory titling) was deliberately left Unassigned rather than force-fit. Caught only by manually tracing where specific real grant titles landed and asking "does this make sense" — no automated test in this repo's suite would have caught it, since the bug produced syntactically valid, internally consistent output. A regression test now exists (`tests/test_keyword_match.py::test_collapse_does_not_degenerate_trailing_symbol_to_a_common_word`).
- **A related, separate tokenization limitation was found during the manual curation pass above — NOT fixed, a genuine design tradeoff.** `kw_vocab.tokenize()`'s `KW_TOKEN_PATTERN` keeps a `/` intra-token so real compounds (`i/o`) survive as one token — but a grant title like `"...Dynamical Systems/Machine Learning Approach"` (no spaces around the slash) tokenizes to `["systems/machine", "learning"]`, not `["systems", "machine", "learning"]`, so the already-curated term `"machine learning"` never matches even though it's right there in the text (confirmed: grant 1570983). Fixing this generically would risk under-tokenizing genuine slash-compounds elsewhere — left as a known, narrow gap rather than special-cased.
- **A second real curation bug (distinct from the `"a+"` collapse bug) was found via manual inspection of the embedding-centroid diagnostic's negative-margin cases** — not a code bug this time, a term-choice bug in the ORIGINAL Phase 4a curation (leaf 10, "Groundwater/Soil Chemistry & Water Quality"). The curated term `"wells"` plural-folds to `"well"` at the stem tier, which then matches the extremely common English adverb "well" ("as well," "well-known") anywhere it appears — **42 of that leaf's 86 assigned grants** (an Osteoarthritis study, a Fermi-level condensed-matter-physics grant, a satellite-servicing SBIR — none groundwater-related) were there purely because of this collision, found by tracing exactly the kind of case the plan's embedding-centroid check is meant to surface (large negative `centroid_margin` = keyword pick and embedding geometry disagree). The leaf's other single-word terms (`water`, `oxygen`, `carbon`, `gas`, `ph`, `bubbles`, `saturation`/`saturated` — the latter also collides with vision-science "color saturation") were confirmed generically risky the same way by inspecting real member grants, not guessed at. Fixed by pruning to the 6 terms actually driving this leaf's high-confidence, genuinely on-theme members (`water quality`, `north carolina`, `coal`, `sodium`, `electrolysis`, `soil`) — every one of the 19 misclassified grants checked individually landed correctly afterward (several exactly where the embedding signal had already suggested, e.g. "Towards Transparency of Personalization on the Web" → Theoretical CS/Network/Data Science). **Lesson for any future curation pass: before curating a single-word term, check whether its stem-folded form collides with a common English word, and treat any confidently-single-word term as higher scrutiny than a multi-word phrase** — the two real bugs found this session (`"a+"`→`"a"`, `"wells"`→`"well"`) were both exactly this failure shape.
- **The embedding-centroid independent-signal check (Step 3 validation) now flags a real, unresolved concern, revised after the bug-fix re-run.** The 610 grants BERTopic left as noise-with-text are now **concentrated in 3 parents** (Computing/Networking/Robotics 27.9%, Social Science/Policy/Workforce 24.8%, Biomedical Sciences 22.5% — 75% combined) — the plan's own named "coverage hole just relabeled" failure signature, not the reassuring "spread out, no concentration" result a pre-bug-fix run had shown. Their mean centroid margin (0.0121) is still measurably below confident docs' (0.0262), so the confidence signal itself isn't obviously broken — but the concentration is worth investigating before trusting this population's labels. The title-only normalization check still fails, and by more than first measured (gap widened 12.2pp→**24.9pp** once the bug's false-positive matches — which had been artificially helping some title-only docs look assigned — were removed); `notebooks/09_keyword_classifier_validation.ipynb` and `src/validate_keyword_classifier.py` both carry the corrected numbers (re-run and re-verified after the fix, not left stale).
- **Parent-theme count dropped 8 → 7, with entirely new names/order** (`PARENT_NAMES` in `src/build_viz_aggregates.py`, byte/value-identical to `docs/TopicVizPrototypes/shared/enrico.js`'s own copy): Biomedical Sciences · Public & Behavioral Health · Environmental Science & Ecology · Social Science, Public Policy & Workforce Development · Materials Science & Structural/Civil Engineering · Mathematics & Fundamental Physics · Computing, Networking & Robotic Systems. The old 8 BERTopic-era names ("Life Sciences & Biomedicine", "Education & Learning", etc.) never matched the curated keyword lists and are gone, not kept as unused history. Leaf count is 31 (was 32) — both counts stay comfortably inside the frontend's pre-allocated color-palette headroom (`TOPIC_COLORS`: 32 slots; `PARENT_COLORS`: 12 slots), so no palette resize was needed this time; `src/build_viz_aggregates.py`'s `validate()` now has a standing informational check for exactly this (`TOPIC_COLOR_CAPACITY = 32`). `what_we_can_see/facets.js` also gained a new "Confidence" facet (ordinal, `none`→`low`→`medium`→`high`) on the Every-Grant grid — a genuinely new capability the old BERTopic one-hot data couldn't support at all (`build_facets()`'s `cols["conf"]`).
- **Validation (post-bug-fix numbers) still shows one real, unresolved calibration problem — not fixed, honestly reported.** The title-only normalization check fails: title-only grants have a **24.9pp** higher low/no-confidence rate than abstract-bearing ones (46.4% vs 21.5%), and — the specific over-boost failure signature the redo plan named in advance — their mean `margin_rel` is *higher* (0.718 vs 0.448 for abstract-bearing), meaning the provisional `W_TITLE=2.0` BM25F constant currently over-boosts short docs rather than fairly normalizing them. This can't be fixed by guessing better constants: `K1=1.5`, `B=0.75`, `ALPHA=0.5`, `W_TITLE=2.0` in `classify_by_keywords.py` are explicitly literature-standard placeholders pending calibration against a **gold set that does not exist yet** — `data/gold/topic_gold_set.csv` (180 rows, stratified) is a scaffold only, `human_parent_label` empty on every row. Parent-level agreement with BERTopic, by contrast, is now solidly healthy (75.5%, see above) once the matching bug was fixed — not a live concern. `notebooks/09_keyword_classifier_validation.ipynb` / `src/validate_keyword_classifier.py` are the source for all of this and were re-run and re-verified after the bug fix, not left stale.
- **Phase 4c (bounded LLM adjudication of the low-confidence tail) is scaffolded, not run** — `src/adjudicate_low_confidence.py`, scoped to `conf_tier ∈ {low, none}` AND `unassigned_reason != "no_usable_text"` (a few hundred docs), Batches API, structured output with a first-class `abstain`. No `ANTHROPIC_API_KEY` is set in this environment and the sandbox only allowlists `pypi.org`, so — same precedent as the NIH RePORTER/NSF Award Search backfill — this needs the user to run it themselves.
- **BERTopic is now historical/comparison-only, not canonical** (SPECTER2 → UMAP → HDBSCAN → c-TF-IDF, 32 topics + noise, `min_cluster_size=20`, re-fit 2026-08-20). Still fit via `src/topics_bertopic.py`, output still `data/processed/topic_assignments.parquet` — nothing about *producing* that file changed, only its role downstream: it's no longer what `build_viz_data.py`/EnricoVis JSON/`TopicVizPrototypes` render, only a `bertopicDom`/`bertopicNoise` comparison column and the `agrees_with_bertopic`/parent-crosswalk validation signal described above. `ARTIFACT_TOPIC_ID` (the old placeholder-title bucket, id 14) is a **BERTopic-era concept**, still meaningful for interpreting `topic_assignments.parquet` on its own terms but retired from every place that used to compare against it directly (`build_viz_aggregates.py`, `kw_review_sheet.py`). ## Conventions & gotchas

- **Never commit notebook outputs.** Use `nbstripout` (in requirements) or "Restart kernel & clear outputs" before `git add`. Notebooks are committed with outputs stripped; the CI executes/renders them.
- **`data/processed/` and `outputs/` are gitignored** (`*.parquet` too), with two targeted exceptions: `outputs/topic_labels.json` (the curated topic-label/parent-theme map) is un-ignored via `!outputs/topic_labels.json`, and — added 2026-08-20 — `data/nih_nsf_backfill/*.parquet` (the NIH RePORTER / NSF Award Search backfill's raw caches + derived tables, deliberately tracked so the rate-limited live fetch never has to be re-run) is un-ignored via `!data/nih_nsf_backfill/` + `!data/nih_nsf_backfill/*.parquet`. Note a bare `outputs/`/`data/nih_nsf_backfill/` directory-level ignore can't be selectively un-ignored by a file-level negation at all; the *parent pattern* has to already be a wildcard-on-contents (`outputs/*`, or here just the blanket `*.parquet` rule) for a file-level `!` to work at all — git can't re-include a path whose parent directory itself is what's excluded. Regenerate everything else with `build_dataset.py`; don't hand-edit parquets.
- **A bare directory-name `.gitignore` entry (`lib/`, `build/`, `dist/`, `var/`, `target/`, `parts/`, `env/`, `venv/`, `instance/`, `cover/` — all present in this repo's `.gitignore`, from the Python-packaging template) matches at ANY depth**, not just the repo root — e.g. a future `docs/TopicVizPrototypes/lib/` would be silently untracked. Before adding a new directory anywhere under `docs/`, check `git check-ignore -v <path>` first; this is exactly what protects `docs/onlineoutput/{data,shared,what_we_can_see,topic_flow,about}/` from ever being committed as duplicated CI-only copies (see the `TopicVizPrototypes/` entry above).
- **Caveat — raw `DataSet/*.xlsx` ARE committed** despite `DataSet/ReadMe.md` and `WEEKLY_PLAN.md` stating raw data should not be. Treat the committed raw files as sensitive; confirm before adding/removing them.
- `scripts/_*.py` are **ad-hoc diagnostics**, not part of the pipeline — but note `_diagnose_orphans.py` and `_orphan_faculty_overlap.py` still **write CSVs into `data/processed/`**, so they aren't purely read-only. The authoritative `personid_to_faculty` comes from `build_dataset.py`, not the looser CSV of the same name from `_orphan_faculty_overlap.py`. `_check_new_abstracts.py` similarly writes `new_abstract_recovery.parquet` into `data/processed/` — an optional input `build_viz_aggregates.py` degrades honestly without (see `docs/data_quality_report.md` §9).
- Several legacy parquets (`grant_faculty`, `grant_text`, `faculty_id_lookup`) still sit on disk from older pipeline versions; the current canonical tables are the 7 listed above (see the "renamed outputs" note in `src/README.md`).
- Join keys are frequently coerced to `str` before merging — do the same to avoid dtype-mismatch silent empty joins.
- Code-quality tools available: `ruff`, `black`, `nbstripout`.
- `src/build_viz_aggregates.py` had three now-fixed bugs worth not reintroducing: the "Other" agency bucket was labeled using the first point's `agencyLabel` (made it look like all "Other" grants were USDA); `viz_meta.json`/`coverage.json` each had a field named `share` meaning different things (dollar-share vs. count-share) — now `unassigned_share_d` / `unassigned.share_n` respectively; and the `abstract_records` missingness grain briefly had a `has_text` field (known only among the 5,095 unmatched-only orphan records, `na` for matched ones) that read as a smaller, contradicting count of the grants-grain's own `Abstract text` field (1,936 known) despite scoring an entirely different population — removed rather than re-captioned, since the funnel section already tells that narrower story more precisely.
- D3/SVG panels: a fixed-CSS-height container paired with a dynamically-sized `viewBox` silently scales all content down as it grows (e.g. more facet-grid bins than fit on screen). Size the container to content (with a sensible floor), not a fixed `vh`.
- `.rowlabel` is a class name shared across the Every grant/Every PI facet grids' row labels and other charts (coverage-by-agency bars, the NIH-vs-NSF cliff chart) in `what_we_can_see.html` — only the facet grids' own row labels need `pointer-events:auto` (scoped via `#facetlabels .rowlabel`/`#pilabels .rowlabel`), so keep future `.rowlabel` changes scoped by id rather than applied to the bare class.
- **When splitting/moving existing code across files, always pull the exact original text (e.g. `git show HEAD:path`) rather than reconstructing a block from inference/pattern-matching** — even when the pattern looks obvious. During the `what_we_can_see.html` module split, `PI_FACET_DEFS.tp` was rewritten from inference instead of read from source: wrong value space, would have silently dropped 46 faculty and crashed on first use (selecting that facet). Caught only by an independent review diff against git history — no static check would have found it, since the fabricated version was syntactically valid and internally consistent.
- **Redefining an existing field's meaning is riskier than it looks — add a new field instead.** During the 2026-08-20 backfill work, `build_viz_data.py`'s `titleOnly` was changed from "does NEU have abstract text" to "did the topic model see abstract text" for 5 grants with borrowed, excluded-from-fit text. That single redefinition cascaded into a `build_viz_aggregates.py` internal-reconciliation assertion (compares `titleOnly`-derived counts against an independently-sourced count that assumed the old meaning), a wrong funnel total, and a display desync in the PI's own EnricoVis apps (which would have shown real text as "title only"). Fixed by reverting `titleOnly` to its original meaning and adding a separate `modelTitleOnly` field for the one place that genuinely needed the new meaning (the abstract-vs-assignment-confidence crosstab) — same lesson as `PI_FACET_DEFS.tp` above: a change that looks locally correct can be silently wrong for every caller that assumed the old contract.
- **NIH RePORTER / NSF Award Search API integration gotchas** (from building `src/backfill_nih_reporter.py` / `src/backfill_nsf_awards.py`): NSF's `awardeeName` search parameter silently **ignores** an unquoted multi-word value — no error, it just returns unfiltered nationwide results for the date range — and must be wrapped in literal double quotes (`"Northeastern University"`) to actually filter; caught only by inspecting a `--limit` smoke test's cached raw records before the full live run, not from any error message. Separately, NSF's `coPDPI` field's real live format (`"First Last email@domain"`, sometimes with a `", Jr."` suffix or a `"(Former)"` annotation) never matched the "Last, First" shape guessed from the (JS-rendered, unreadable) written API docs — always verify a guessed external API field format against one real live response before trusting it, especially when the written docs can't be read directly.
- **d3's keyed `enter().append()` inserts a new node at the end of its parent when nothing follows it in that selection** — joining several different-kind sections (headers/cells/marks/selection-ring) directly onto one shared parent `<g>` works on the *first* render only; once any section's join set changes shape (e.g. Rows switched from "— none —" to a multi-level facet), newly-entering nodes from an earlier section land *after* nodes from a later section that already existed, breaking assumed paint/hit-test order. This silently broke mark hover tooltips for every row past the first once Rows held a real facet (`rect.binhit`'s `fill:transparent` still captures pointer events, unlike `fill:none`, so the mis-ordered hit-rect swallowed `mousemove` before it reached the mark underneath — clicking still worked throughout, since it has its own handler, which was the tell). Fixed in `grid.js`'s `createGrid()` by giving each section a persistent, fixed-order layer `<g>` (`hdrLayer`/`emptyLayer`/`cellLayer`/`markLayer`/`ringLayer`) created once and reused every render, rather than joining straight onto the shared `plotroot` — don't flatten this back to one parent.
- **No browser is available in this working environment** for `TopicVizPrototypes` HTML/JS changes (confirmed across multiple sessions). Verification relies on `scripts/_check_topicviz.py`: an `HTMLParser` tag-balance check + a re-inlining regression guard, a node-based ES-module import-graph/named-export/cycle check (`node --input-type=module --check <file` — bare `node --check somefile.js` silently exits 0 on broken module syntax in a `.js` file, confirmed on node v22.14.0; always read from stdin with `--input-type=module`), a per-page id cross-reference over each page's reachable modules, and the dataset-wiring reconcile (`--data-only`). These catch structural breakage but never confirm actual rendering/layout/interaction, and can't see an `await`-ordering race (a render running before its `fetch()` resolves) at all. Treat every such change as needing a real-browser check before publishing — serve the directory (`python -m http.server 8000 --directory docs/TopicVizPrototypes`; the pages `fetch()` their data and do NOT work over `file://`) — and say so explicitly rather than implying it was visually confirmed.
